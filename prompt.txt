# CampuSync — Master Project Development Plan

## 1. Project Overview

Build a complete college management system called **CampuSync** for **KVG College of Engineering (KVGCE)**.

CampuSync will manage:

* Student admissions
* Student accounts
* Staff/faculty accounts
* Academic structure
* Subjects
* Attendance
* Mentor-student assignments
* Low-attendance cases
* Attendance shortage reasons
* Supporting certificates/documents
* Fees
* Fines
* Email communication
* Password management
* Role-based access control
* Audit history

The current version is specifically designed for **KVGCE**.

Do not introduce multi-college or multi-tenant functionality unless explicitly requested later.

---

# 2. User Types

CampuSync will have the following user types:

## 2.1 Admin

Admin has complete access to the system.

Admin can manage:

* Students
* Staff
* Admission staff
* Courses
* Batches
* Semesters
* Sections
* Subjects
* Mentor assignments
* Attendance
* Fees
* Fines
* Student accounts
* Staff accounts
* Uploaded certificates
* System settings
* Audit records

---

## 2.2 Admission Staff

Admission staff handles student admission and registration.

Admission staff can:

* Create new student records
* Enter student personal information
* Enter academic information
* Assign course
* Assign batch
* Assign semester
* Assign section
* Create student accounts
* Generate temporary credentials
* Trigger account-creation emails
* View and manage admission records

Admission staff must not automatically have full Admin permissions.

---

## 2.3 Staff / Faculty

Staff members are faculty members.

Staff can:

* Log in
* Manage their own subjects
* Handle assigned classes
* Record attendance for their own subjects
* View attendance records related to subjects they handle
* Manage their own profile

Faculty must not be able to see a student's overall attendance percentage simply because they teach that student.

Faculty primarily manages attendance for their own subjects.

---

## 2.4 Mentor

A Mentor is **not a separate user type**.

A Mentor is a Staff/Faculty member who has been assigned a group of students.

Therefore:

```text
Staff
  |
  └── Mentor Assignment
          |
          └── Assigned Students
```

A staff member can simultaneously:

* Teach subjects as Faculty
* Act as a Mentor

Mentor functionality should become available to a Staff account when that staff member has assigned students.

A mentor can:

* View assigned students
* View assigned students' attendance
* Identify students below 85% attendance
* Add attendance-shortage reasons
* Upload valid supporting certificates/documents
* View relevant student information

A mentor must not see students who are not assigned to them.

---

## 2.5 Student

Students can:

* Log in
* View their profile
* View academic information
* View their mentor
* View attendance
* View subject-wise attendance
* View fees
* View fines
* Change their password

Students cannot:

* Modify attendance
* Modify academic information
* Modify mentor assignment
* Modify fees
* Modify fines
* Access another student's information

---

# 3. Authentication

Authentication must be implemented before the main application modules.

Create a login system that identifies the authenticated user's role and redirects them to the appropriate section.

Required protected areas:

```text
/admin
/admission
/staff
/student
```

Authentication must support:

* Login
* Logout
* Password hashing
* Session management
* Protected routes
* Role-based authorization
* Password change
* Forgot password
* Password reset
* Temporary-password handling

Never store plain-text passwords.

---

# 4. Role-Based Authorization

Authorization must be enforced on both:

1. Frontend routes
2. Backend/API operations

Do not rely only on hiding frontend buttons.

Every protected API operation must verify the authenticated user's permissions.

### Student

Cannot access Admin or Admission functionality.

Cannot modify attendance.

### Staff

Can manage authorized subjects and attendance.

Cannot access Admin functionality.

### Mentor

Can access only assigned students.

### Admin

Has full authorized system access.

---

# 5. Academic Structure

The academic structure must be configurable.

Use:

```text
Course
   ↓
Batch
   ↓
Semester
   ↓
Section
   ↓
Students
```

Example:

```text
CSE
 └── 2025 Batch
      └── Semester 3
           ├── Section A
           ├── Section B
           └── Section C
```

Do not hardcode the number of sections.

Different batches can have different numbers of sections.

Authorized administrators must be able to manage:

* Courses
* Batches
* Semesters
* Sections

---

# 6. Student Admission

Create a complete admission workflow.

## Personal Information

Store:

* Full name
* Date of birth
* Gender
* Phone
* Email
* Address

## Academic Information

Store:

* Course
* Department
* Batch
* Semester
* Section
* Admission year

## Registration Information

Store:

* Temporary registration number
* USN when available

A newly admitted student may initially have a temporary registration number.

The official USN may be added later.

When the official USN becomes available:

* Update the existing student record
* Do not create a new account
* Preserve existing attendance and historical data

# 8. Staff Management

Admin must be able to:

* Create staff accounts
* Edit staff accounts
* Activate/deactivate staff accounts
* View staff details
* Assign/manage subjects
* Manage staff information

A staff member can handle multiple subjects where authorized.

---

# 9. Subject Management

A subject should contain information such as:

* Subject name
* Subject code
* Course
* Batch
* Semester
* Section
* Assigned faculty

Faculty should only be able to manage attendance for subjects/classes they are authorized to handle.

---

# 10. Attendance System

Attendance is a core CampuSync feature.

Attendance must be recorded:

* Subject-wise
* Class/session-wise
* Student-wise
* Date-wise

Faculty workflow:

```text
Select Subject
      ↓
Select Batch
      ↓
Select Semester
      ↓
Select Section
      ↓
Select Date/Class
      ↓
Load Students
      ↓
Mark Attendance
      ↓
Save
```

Attendance status:

```text
Present
Absent
```

Store:

* Student
* Subject
* Faculty
* Batch
* Section
* Date
* Class/session number
* Attendance status
* Created timestamp
* Updated timestamp

---

# 11. Number of Classes

The number of classes is not fixed.

Faculty/staff will provide the relevant class/session information.

Example:

```text
DBMS

Total Classes: 44
Student Present: 37
```

CampuSync must calculate:

```text
Attendance Percentage =
Present Classes / Total Classes × 100
```

Example:

```text
37 / 44 × 100 = 84.09%
```

Faculty must not manually calculate percentages.

---

# 12. Faculty Attendance Restrictions

Faculty can manage attendance for their own authorized subjects.

Faculty should not automatically see:

* Overall student attendance
* Attendance from unrelated subjects
* Other faculty's attendance records
* Mentor-only information

Faculty should only have the access necessary to perform their academic responsibilities.

---

# 13. Student Attendance

Students can view their own attendance.

Attendance must be available subject-wise.

Example:

```text
DBMS                  84%
Operating Systems     91%
Java                  88%
Computer Networks     79%
```

Attendance percentages must be calculated automatically from attendance records.

Students cannot modify attendance.

---

# 14. Mentor System

A Staff member can become a Mentor.

Do not create a separate Mentor user account type.

Instead, create a mentor assignment relationship between:

```text
Staff
   ↓
Mentor Assignment
   ↓
Student
```

A mentor can have multiple students.

The number of students must not be hardcoded.

A student can have only **one active mentor at a time**.

---

# 15. Mentor Assignment

Staff can assign themselves as mentors according to the project's mentor workflow.

Mentor assignments should be stored separately from the Staff record.

A mentor assignment should contain:

* Staff/Mentor
* Student
* Academic year
* Start date
* End date
* Status

A student's mentor can change when the appropriate academic-year transition occurs.

Example:

```text
Year 1
Student → Mentor A

Year 2
Student → Mentor B

Year 3
Student → Mentor B

Year 4
Student → Mentor B
```

Historical assignments must not be deleted or overwritten.

Students cannot change their own mentor.

---

# 16. Mentor Dashboard

A Staff member with mentor responsibilities should have access to:

```text
My Students
Low Attendance
Attendance Issues
```

The mentor can view assigned students and their relevant attendance information.

The mentor must not be able to access unrelated students.

---

# 17. Low Attendance

CampuSync must identify students below the required attendance threshold.

Default threshold:

```text
85%
```

Preferably make the threshold configurable by Admin.

Example:

```text
Student: Rahul
Attendance: 82%
Status: Below Required Attendance
```

Mentors should have a dedicated way to identify these students.

---

# 18. Attendance Shortage Reason

When a student falls below the required attendance threshold, the mentor can record the reason.

The mentor can enter:

* Reason
* Remarks
* Date
* Supporting document/certificate

Possible reasons include:

* Medical issue
* Approved college activity
* Personal reason
* Other valid reason

These should not be hardcoded as the only possible options.

---

# 19. Supporting Certificate

Mentors can upload valid supporting documents.

Examples:

* Medical certificate
* Supporting letter
* Other valid certificate/document

Store:

* File reference/path
* Original filename
* File type
* Upload date
* Student
* Mentor
* Related attendance issue

Use proper file storage rather than storing large files directly inside relational database fields.

---

# 20. Attendance Issue History

Never overwrite previous attendance-shortage reasons.

Maintain an issue history.

Each attendance issue can contain:

```text
Student
Reason
Remarks
Certificate
Mentor
Date
Created At
```

This allows the institution to maintain historical records.

---

# 21. Fees

If the Fees module is included, authorized users can manage:

* Fee type
* Amount
* Due date
* Payment status
* Payment date
* Student

Possible statuses:

```text
Paid
Pending
Partial
```

Students can view their own fee information.

Students cannot modify fee records.

---

# 22. Fines

Fines should contain:

* Student
* Reason
* Amount
* Date
* Status
* Payment information where required

Example:

```text
Library Fine
Amount: ₹100
Status: Pending
```

Students can view their own fines.

Students cannot modify fines.

---

# 23. Email System

Use a transactional email provider such as **Resend**.

Email functionality should include:

* Student account creation
* Temporary password delivery
* Password reset
* Important account notifications

Use a verified CampuSync domain and appropriate sender address.

Never expose email API keys in frontend code.

Use environment variables for secrets.

---

# 24. Password Reset

Implement a secure password reset process.

Flow:

```text
Forgot Password
      ↓
Enter Email
      ↓
Generate Secure Reset Token
      ↓
Send Reset Email
      ↓
Open Reset Link
      ↓
Set New Password
      ↓
Invalidate Token
```

Reset tokens must:

* Be cryptographically secure
* Expire
* Be single-use
* Not expose passwords

---

---

# 26. Important Database Rules

### Student

One student should have one primary user account.

### Mentor

One student can have only one active mentor at a time.

### Staff

One staff member can handle multiple subjects.

### Attendance

An attendance record must belong to the correct:

* Student
* Subject
* Class/session
* Date

Duplicate attendance records for the same class/session must be prevented.

### Academic Structure

Sections must belong to the correct academic structure.

# 31. Error Handling

Handle:

* Invalid login
* Expired session
* Unauthorized access
* Missing records
* Duplicate records
* Invalid attendance
* Invalid file uploads
* Failed emails
* Database errors
* Invalid form input
* Expired password reset tokens

Do not expose internal database errors or secrets to users.

---

# 32. Development Strategy

Do not generate the entire application blindly in one step.

Build the application incrementally.

For every phase:

1. Plan database changes
2. Implement database changes
3. Implement backend/business logic
4. Implement APIs
5. Implement authorization
6. Implement the required functionality
7. Test it
8. Fix errors
9. Verify the complete workflow
10. Move to the next phase

Do not build dependent modules before their underlying modules work.

---
